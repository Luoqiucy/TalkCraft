# TalkCraft 多轮上下文与长期记忆专项验收

日期：2026-10-01  
阶段：Phase 2 商业化软件路线  
目的：验证多轮问题是否继承了正确信息、个人记忆是否真实保存与隔离，并根据失败修复生产调用链。

## 安全范围与运行命令

离线验收使用临时目录、临时 SQLite、临时 HTTP 端口和合成账号；不会写入用户正式历史、长期记忆、账号、用量、额度或录音。只读历史审计直接读取 `C:\Users\1\AppData\Local\TalkCraft\history\records.json`，记忆数据库使用 SQLite 只读模式；审计没有调用会初始化、清理或改写用户数据的存储接口。

默认固定样本命令：

```powershell
npm run acceptance:context-memory
npm run acceptance:memory-benchmark
```

第一条会检查 12 组连续会话、实际本机 `/api/agent`/Daisy 循环、账号网关、长期记忆和同步生命周期。第二条只创建临时合成资料，按 100、1,000、10,000 条测量查找。

真实模型与联网测试不会随普通测试启动，需明确设置 `TALKCRAFT_LIVE_ACCEPTANCE=1` 后运行 `npm run acceptance:context-memory:live`。脚本从当前 `.local/asr-test.env` 读取已配置提供器，但不打印密钥；每个任务沿用 45 秒总时限、最多 6 次实际工具调用，数据写入临时目录。当前批次的 12 个真实任务额度已用完；后续只有用户再次安排真实复测时才运行。

## 基线和判定

修改前的专项失败基线为 12 组连续对话中 5 组通过、9 个场景断言失败。真实历史补充了生产端样本，但历史来源只在数据实际保存时作为证据：旧记录没有逐工具轨迹的地方标“未记录”，不能推测具体调用。

通过不能只看回答是否有文字。每轮还要检查原始输入、有效问题、行为类型、对象、字段来源、继承/清除/撤销情况、路由、实际工具参数、日期范围、记忆命中 ID 和来源依据。账号隔离、删除后仍注入、未授权写入、私人信息进入公开搜索任一发生都判失败。部分答案与合理澄清按其证据和缺失字段评估，不要求无资料时编造答案。

## 固定连续会话

测试在每组的真实会话历史上逐轮调用解析器，并给每一轮注入 sessionId/taskId，检查原话、解析问题、动作和字段来源。会话包含：

1. MacBook Pro → 2021 款 → 16 英寸/M1 Pro → 32GB/512GB → 用户买价 6700 元 → 闲鱼近期成交价。购买价只属于用户自述。
2. 笔记本切换 iPhone 13 Pro Max，清掉芯片、内存、存储和购买价，但保留适用的闲鱼成交价任务。
3. 只说“那手机呢”时追问缺少型号，不猜具体设备。
4. vivo 最新手机/价格/配置 → OPPO → 发布时间；替换品牌，不继承旧型号。
5. 比较两款手机后问“它的续航”，多对象指代未能唯一确定时只澄清。
6. 张家港 → 南京 → 杭州 → 明天；工具参数与地点变化一致。
7. “未来一周天气”→“南京的”，恢复待补地点任务，保留原范围。
8. 同句把未来一个月改成未来一周，只保留最终范围。
9. 跨轮把未来一个月改成未来一周，保留地点并记录被撤销范围。
10. 小米汽车近期新闻 → 谷歌 → 最近三天，区分公司、任务和日期窗口。
11. 产品→天气→普通知识及清空会话，不继承旧商品字段、地点或价格平台。
12. 喜欢香蕉、偶尔吃苹果、查询苹果好处，分别表示偏好、行为频率和公开问题。

额外断言：单独说“杭州”或“那杭州呢”时，不能把城市重复拼成“杭州 杭州”；换话题后用户只说“那明天呢”时，不复用旧地点，而要询问城市。

## 长期记忆、账号同步与检索规模

44 个独立语义样本覆盖水果偏好与频率、饮品、回答风格、默认地区、项目和个人词条。它们逐条检查检索的 memoryId 与领域，避免“偶尔吃”被升级成喜欢，或不同领域互相命中。现有生命周期测试另覆盖写入需确认、更新冲突、暂停学习、关闭使用、删除、来源历史联动、导出范围及用户事实来源。

新增独立 Node 子进程重启用例：一个进程保存已确认偏好并产生待同步操作后退出；新进程重新打开同一隔离库，重新命中记忆并重试同一 operationId，确认回执后队列清空。既有双隔离客户端用例检查账号同步、重试幂等、冲突、删除墓碑、游客与账号隔离、未授权同步拒绝。这是同机开发服务替身，不代表公网跨设备云服务上线。

规模测试每档执行 30 次检索，合成数据只保留一个最早目标记忆，其余为无关合成项；检验相关/无关查询和“最新小窗口”不漏掉旧条目。它不是覆盖所有中文意图的语义准确率测试。

## 真实历史审计

审计找到 28 条指定历史记录。关键观察：

- `2f2b35fc-9628-4f48-985b-2f38ad516fea`（“OPPO 手机呢？”）的保存搜索状态为 `not-needed`、`performed:false`，符合当时未搜索记录。
- `d95f6582-9d70-40d3-8313-3babb13c786d` 的保存状态为 `page-read`，但原始对话里用户明确要求继承 vivo 查询任务；这不证明所读页面确实回答了 OPPO 的价格/配置。
- 南京补地点链：`c97db041-6bf0-4361-a4d2-bbe256f1d970` 保存 `not-invoked`；`151a71e1-a680-4b84-bc1a-19a4f5256778` 保存 `not-needed`。地点补全后没有真实天气调用证据。
- `ae59cd39-664f-4ccb-afa1-702b640b20cb` 保存 `not-invoked`。`aafa76fe-2935-4d12-9fd6-26bd5c03fc93` 只保留了 ASR 阶段尝试，没有 Agent 搜索轨迹，不能断言后端工具参数。
- `d8689816-9f4f-4ace-8103-edc9b07caa19` 保存 `weather-data`，但旧记录没有逐工具参数，无法验证“未来一周”覆盖是否正确。
- 香蕉记录 `93b51fea-b77f-4fb6-8007-cc5112393ae2` 的回答被存为文本，搜索状态是 `not-needed`；只读 SQLite 查询显示当时正式本地记忆表无任何记忆行。因此“助手说记住了”没有持久化证据。
- 指定的小米新闻、设备和价格记录部分含搜索状态，但旧 schema 未保存工具调用明细；未记录不等于没有发生。

## 修复与自动结果

真实请求失败促使生产修复：天气新地点追问识别“那杭州呢”，把时间短语与地点分开；在天气工具执行前按同一结构化请求补全规范参数，不采信模型漏传/乱填的字段；日期改口由当前地点承接；换话题后的模糊“明天”不再借用过期地点；无地点请求不会触发模型或工具。产品换对象时，含具体型号与成交平台的问句不再被误判为纯约束追问；“新闻报道”中明确问手机型号时优先按产品问题解析，而不是公司新闻。

更新后验证：

- `npm run acceptance:context-memory`：68/68 专项测试通过；生产 HTTP 模拟天气链路断言三次调用参数依次为南京/current-today、杭州/current-today、杭州/next-seven-days。
- 全量 `node --test --test-concurrency=1`：538/538 通过。
- `npm run check`、`npm run react:check`、`npm run react:build`：均通过。
- `npm run acceptance:memory-benchmark`：结果如上。
- 真实模型/联网：本轮 12 个任务已完成，但真实天气追问暴露的问题尚未发起付费复测；本地端到端替身通过不代表云端复测通过。
- Windows 桌面：源码构建版需重新更新 EXE 后再人工启动验收；透明窗、快捷键、用户数据迁移和登录态切换没有因本报告被视为实机通过。

## 待验收及用户手动步骤

以下不超过 5 项，运行新构建开发版后可手动检查：

1. 连续问“南京今天的天气怎么样？”→“那杭州呢？”→“哦不对，未来一周。”；确认第二轮切换杭州，第三轮保留杭州并只回答未来七天范围。
2. 先问南京天气，再切换话题讨论蓝牙，然后问“那明天呢？”；应用应询问地点，不得用南京天气回答。
3. 问“未来一周天气怎么样？”后答“南京的”；应在相同任务里补城市，不再要求重讲查询。
4. 问 MacBook 配置后再问“那你帮我查一下苹果13 Pro Max在闲鱼的近期成交价格”；检查新请求不携带 MacBook 芯片、内存、存储或购买价。
5. 在隔离账号的记忆设置中确认一条回答偏好，重启后查询，再用“这次详细说”覆盖；确认答案采用这次要求且未改写长期偏好。
