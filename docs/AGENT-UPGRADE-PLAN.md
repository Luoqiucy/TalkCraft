# 联网问答 Agent 升级建议与开发计划书

更新：2026-11-13。本文是建议和计划，不代表已实现。依据是本机问答历史（只读分析，未上传）、当前代码，以及近期开源语音助手项目的做法（见文末参考资料）。

## 1. 结论

TalkCraft 现在的问答链路是：**先用正则规则理解问题，再交给 DeepSeek 调用工具，最后由程序规则判断证据够不够、要不要替换回答**。规则一旦理解错，后面的搜索、证据检查和回答都会跟着错，这是历史中多数问题的根源。

近期开源项目（Pipecat、LiveKit Agents、小智 xiaozhi-esp32-server 等）的共同做法是：**理解问题交给大模型（问题改写 + 函数调用），程序只管理上下文、记忆、工具和安全边界**。

建议按这个方向分阶段改造：

1. 新增“问题改写器”：每次续问先调用一次轻量模型，输出结构化 JSON（完整问题、意图、对象、地点、时间范围、搜索词）。现有正则降级为校验和兜底。
2. 放宽程序对回答的硬替换，改为“保留有引用的回答 + 标注缺口”。
3. 长对话改为“摘要 + 按空闲时间分段”，取代现在的硬截断，界面上显示上下文状态。
4. 国内地名改用国内地理编码服务，天气数据仍用 Open-Meteo。
5. 长期记忆保持“用户确认才保存”的原则，改为由模型提出候选、用户确认，检索改用 SQLite FTS5。
6. 先建离线评测集，每一步都用同一批历史问题量化对比，不凭感觉判断是否改好。

## 2. 现状诊断（数据来自本机历史）

统计范围：2026-10-01 至 2026-11-12 的 77 条记录（问答 70 条），上下文重放用全部 217 条问答原话。

| 问题 | 数据 | 根因 |
|---|---|---|
| 回答被替换成固定拒答 | 历史中 24 次“已查询，但现有资料仍不足以核实完整请求”，每次都查到 5–40 条来源 | 程序从语音原话提取的“对象”是错的（如“小米刚发布的这个鹏程N70”“你能看到我位置”），核对失败后整段替换。#19 已放宽 |
| 续问接错上下文 | “那里有什么好玩的”拼上 6 问之前的“小米”；“那比亚迪汽车呢”仍查小米；“款的苹果”进入每次搜索 | 正则把“那”当产品指代，没有话题切换概念。#18 已修复已知模式 |

| 语音识别失败 | 70 次 ASR 中 13 次失败、6 次取消或被打断；13 次失败都发生在 2026-11-05 修复之前，多数提示“请检查网络、凭据” | #2 已接入新版 Key 并区分“未识别到语音”，之后需继续观察 |
| 重启后丢失语音问题的上下文 | 90% 的问答是语音输入，重启后这些问题全部不恢复 | 只读 `revisedText`，语音问题存在 `originalTranscript`。#18 已修复 |

待合并的修复：#17（天气前缀）、#18（续问上下文）、#19（保留有引用的回答、天气地点排序、搜索词）。本计划在它们之上继续推进。

## 3. 技术栈变更

### 3.1 保留

| 部分 | 现有技术 | 保留理由 |
|---|---|---|
| 桌面壳与界面 | Tauri + React 19 + Vite | 与本次问题无关 |
| 本地服务 | Node.js（ESM）`server.mjs` | 工具、证据、历史都在这里，改造成本最低 |
| 问答主模型 | DeepSeek（`deepseek-v4-flash`），流式 Function Calling | 已接通流式回答与工具调用 |
| Agent 循环 | 自写的 Daisy 循环 `src/agent/daisy-question.mjs` | 已有预算、取消、来源、引用和流式撤回逻辑。不建议整体换成 LangGraph，迁移风险大于收益 |
| 搜索与读页 | DeepSeek 原生搜索 / Firecrawl、本地读页 | 先修理解层，搜索源以后再评估 |
| 天气数据 | Open-Meteo 预报接口 | 免费、无 Key，工具已支持按坐标查询 |
| 语音识别 | 火山引擎（豆包）流式 ASR | #2 已接入新版 Key |
| 记忆存储 | `node:sqlite`（WAL） | 已验证本机 Node 内置 SQLite 3.51.2，支持 FTS5 与 `trigram` 中文分词 |
| 结构化校验 | `zod`（已是依赖） | 直接用于问题改写器的输出校验，不需要新增依赖 |

### 3.2 新增

| 新增项 | 技术选择 | 用途 | 新依赖 |
|---|---|---|---|
| 问题改写器 | DeepSeek `deepseek-v4-flash`，JSON 输出模式，`temperature: 0`，`zod` 校验 | 把续问改写成完整问题，并给出意图、对象、地点、时间范围和 1–3 条搜索词 | 无 |
| 离线评测集 | 从本机历史抽取并脱敏的约 200 条多轮问答，加人工标注的期望结果；`node --test` 脚本 | 每次改动都量化上下文理解准确率、拒答率和地点命中率 | 无 |
| 对话摘要 | 同一个轻量模型，在历史超出预算时把较早几轮压缩成 300 字以内的摘要 | 替代现在“超过 12 条或 8000 字就丢掉最早一轮”的做法 | 无 |
| 国内地理编码 | 高德 Web 服务“地理编码”或和风天气 GeoAPI（二选一，需申请 Key） | 把“荥阳”“固安”“张家港”准确解析成坐标，再交给 Open-Meteo 查预报 | 无（HTTP 调用） |
| 记忆全文检索 | SQLite FTS5，`tokenize='trigram'` | 中文记忆按内容检索，取代现在的逐条匹配 | 无（Node 内置） |
| 候选记忆 | 模型从对话中提出“可能值得记住”的事实，**由用户确认后才保存** | 取代“我喜欢吃 X”这类正则抽取，同时保持现有隐私原则 | 无 |
| 观测记录 | 历史执行记录新增改写器输入摘要、输出 JSON、耗时、词元数和是否回退 | 线上问题能直接定位到理解错还是搜索错 | 无 |

### 3.3 替换

| 现在 | 替换为 | 说明 |
|---|---|---|
| `question-context.mjs` 中由正则决定意图、对象和地点 | 问题改写器给出结果，正则只做校验和超时兜底 | 正则保留，但不再是主路径 |
| 程序强制首轮调用某个工具 | 只有天气保留强制；其他问题由模型通过 Function Calling 选择工具 | 与小智等项目推荐的 `function_call` 方式一致 |
| `evaluateSearchEvidence` 用正则对象核对来源 | 用改写器给出的对象核对；核对不通过时只加提示，不整段替换（#19 已开始） | 新闻的日期范围检查保留 |
| Open-Meteo 地理编码 | 国内地理编码作为主路径，Open-Meteo 地理编码作为海外地点和失败时的回退 | 预报接口不变 |
| 对话历史按条数和字数硬截断，重启后不限时间恢复 | 摘要加按空闲时间分段（建议空闲 2 小时开新对话），界面显示“正在使用之前的对话”并提供“新对话”按钮 | 避免几天前的对话影响今天的问题 |

### 3.4 暂不引入

| 方案 | 不引入的原因 |
|---|---|
| 整体迁移到 Pipecat 或 LiveKit Agents | 它们是 Python 实时语音框架，面向连续通话和 WebRTC。TalkCraft 是按键录音的桌面应用，主要问题在理解层，不在音频管线 |
| Letta（MemGPT） | 社区反馈实际使用中常出问题；它要求 Agent 自己改写记忆，与“用户确认才保存”的原则冲突 |
| Zep / Graphiti 知识图谱记忆 | 需要额外的图数据库服务；当前记忆量很小，SQLite 足够。以后需要区分“以前喜欢”和“现在喜欢”时再评估 |
| 向量数据库（ChromaDB 等） | 记忆和对话量小，FTS5 足够；以后需要语义检索时可先评估 `sqlite-vec`，仍放在同一个 SQLite 文件里 |
| 语义轮次检测（Smart Turn、turn-detector） | 只在免按键连续对话时才需要，列入远期 |

## 4. 目标架构

```text
语音 / 文字输入
   │  （ASR 原文保留，不改写用户原话）
   ▼
① 上下文准备（程序）
   - 当前对话：最近 N 轮原话 + 较早轮次的摘要
   - 按空闲时间分段；“新对话”立即清空
   - 规则提示：最近提到的地点、产品（来自现有正则，仅作参考）
   ▼
② 问题改写器（一次轻量模型调用，JSON）
   - 有历史时才调用；首问或明显独立的问题直接跳过
   - 超时 / 输出不合法 → 回退到现有规则结果
   ▼
③ 程序校验（防止模型编造上下文）
   - 改写出的地点、品牌、型号必须出现在当前问题或历史原话中
   - 不满足时丢弃该字段，或请用户澄清
   ▼
④ Daisy 工具循环（DeepSeek Function Calling）
   - 天气：强制 get_weather（国内地理编码 → Open-Meteo 预报）
   - 其他：模型自选 search_web / read_webpage / scrape_webpage
   - 搜索词：优先使用改写器给的 searchQueries，程序只补遗漏的型号
   ▼
⑤ 回答后处理（程序）
   - 有引用：保留，并标注缺口
   - 无引用的肯定回答：加提示或拒绝采用
   - 新闻：保留日期范围检查
   ▼
⑥ 记忆（异步，不阻塞回答）
   - 模型提出候选记忆 → 界面提示 → 用户确认后写入 SQLite
```

## 5. 实施步骤

每个阶段单独一个分支和 PR，按 `docs/RELEASE.md` 写 CHANGELOG，CI 通过后再合并。每个阶段都用第 5.1 节的评测集对比改动前后的结果。

### 5.1 阶段 1：评测集与基线（先做，其余阶段都依赖它）

1. 写脚本 `scripts/build-context-eval.mjs`：从本机历史读取问答，按会话（空闲超过 2 小时就切开）还原成多轮对话，输出到 `.local/eval/`。这个文件只留在本机，不提交。
2. 人工从中挑约 200 条，重点覆盖历史中出过错的类型：地点指代、产品指代、换对象、换话题、语音错字、天气前缀、记忆问题。去掉个人信息后，改写成测试夹具 `test/fixtures/context-eval.json`，可以提交。
3. 每条标注期望结果：`standaloneQuestion`（完整问题）、`intent`、`subject`、`location`、`followUp`（是否续问），以及“必须不出现”的词（如旧品牌）。
4. 新增 `npm run eval:context`：
   - 规则模式：离线运行，进 CI。
   - 模型模式：需要本机 Key，手动运行，输出准确率表和逐条差异，不进 CI。
5. 记录基线：现在规则方案的准确率，以及历史中的拒答率、天气“没有找到该地点”比例、各类问题的 P50/P90 耗时。

完成标准：评测集提交，基线数字写进 `docs/PROGRESS.md`。

### 5.2 阶段 2：问题改写器

1. 新建 `src/agent/query-rewriter.mjs`：
   - 输入：当前问题、最近 4 轮原话（回答截取前 300 字）、较早轮次的摘要、规则给出的提示、当前日期。
   - 输出用 `zod` 定义：

     ```js
     const RewriteResult = z.object({
       standaloneQuestion: z.string().min(1).max(500),
       followUp: z.boolean(),
       intent: z.enum(['weather', 'product-research', 'company-news', 'news-search', 'time-sensitive', 'general', 'personal-memory', 'url-read']),
       subject: z.object({ brand: z.string(), model: z.string(), category: z.string() }).partial(),
       location: z.string().max(40).optional(),
       timeScope: z.string().max(40).optional(),
       searchQueries: z.array(z.string().max(80)).max(3),
       needsClarification: z.boolean(),
       clarificationQuestion: z.string().max(120).optional(),
     });
     ```

   - 调用参数：`temperature: 0`、最多输出 300 词元、超时 2.5 秒。优先用 JSON 输出模式；如果当前模型不支持，就定义一个工具，用强制工具调用拿到结构化参数。
   - 提示词要求：只能使用对话中出现过的对象和地点；不确定就设 `needsClarification`；保留用户原意，不补充用户没问的内容。
2. 新建 `src/agent/rewrite-guard.mjs` 做程序校验：
   - 改写结果中的地点、品牌、型号，必须能在当前问题或历史原话中找到（允许别名，比如 iPhone 对应苹果）。
   - 找不到就丢弃该字段。
   - 意图是天气但没有地点时，走现有的澄清流程。
3. 接入点：`server.mjs` 的两个问答入口和 `src/commercial/gateway.mjs` 都调用 `resolveQuestionContext`，改为统一调用新函数 `resolveQuestion()`：先跑规则，再按开关调用改写器，最后合并结果。
4. 加开关 `AGENT_QUERY_REWRITER=rules|shadow|llm`：
   - `shadow`：仍按规则回答，同时记录改写器的结果，用来对比。
   - 先在本机用 `shadow` 跑一到两周，评测和线上对比都达标后，再切到 `llm`。
5. 省时：没有历史的首问，或者明显独立的问题（带完整城市、品牌和型号），跳过改写器。
6. 测试：
   - 用假模型覆盖各种情况：正常、超时、输出不合法、编造地点被校验拦下。
   - 评测集模型模式的准确率高于规则基线。

完成标准：评测集上下文理解准确率不低于规则基线加 10 个百分点（目标值，在阶段 1 拿到基线后再定）；新增耗时 P50 不超过 800 毫秒；模型超时或出错时 100% 回退到规则。

### 5.3 阶段 3：工具选择与证据检查

1. `daisy-question.mjs`：
   - 首轮只对天气强制调用工具；产品、新闻等问题设 `tool_choice: auto`，同时在系统提示中说明“需要实时信息时必须调用搜索”。
   - 改写器给出 `searchQueries` 时，作为首轮搜索的建议传给模型；`validatePlannedSearchQuery` 只补遗漏的型号。
2. `search-orchestrator.mjs` 的 `evaluateSearchEvidence` 改用改写器给出的 `subject` 判断对象是否匹配，不再从原话里正则提取。
3. 回答后处理统一成三类：
   - 有引用：保留，并标注缺口。
   - 无引用的肯定回答：加提示；完全没有来源时拒绝采用。
   - 新闻日期范围：保持现有检查。
4. 减少“证据检查不通过就退回模型重写”的轮次：最多一次，并且只在有新证据时触发。

完成标准：历史重放中固定拒答的次数降到 0；产品问题的模型调用次数 P50 减少一轮；P90 耗时下降（目标 20%，以阶段 1 基线为准）。

### 5.4 阶段 4：对话上下文与会话管理

1. `src-ui/src/services/conversationMemory.ts`：
   - 会话按空闲时间切分（默认 2 小时，可在设置中调整）。重启后只恢复最近一段会话。
   - 历史超出预算时，不再直接丢掉最早一轮。改为调用一次摘要（后端新接口 `POST /api/conversation/summary`），把较早几轮压成 300 字以内的摘要，作为一条系统说明随请求发送。
2. 后端 `validateHistory` 支持一条摘要消息，并限制长度。
3. 界面（`WorkbenchApp.tsx`）：
   - 问答区显示“正在使用之前 N 轮对话”。
   - 提供“新对话”按钮，点击后清空当前会话和摘要，不影响历史记录。
   - 用户说“重新开始”“换个话题”时，也开新对话。
4. 测试：会话切分、摘要失败时回退到截断、新对话清空。

完成标准：几天前的对话不再进入今天的上下文；长对话中，第 1 轮提到的地点在第 10 轮仍能正确接上（评测集新增此类用例）。

### 5.5 阶段 5：国内地理编码

1. 用户先选定服务商并申请 Key（见第 8 节）。Key 只放本机配置或账号网关，不进源码和日志。
2. 新建 `src/tools/geocode-cn.mjs`：输入地名，输出坐标、省、市、区县和可信度。只接受行政区级结果，不接受村、路名。
3. `weather.mjs`：
   - 有国内 Key 时先查国内地理编码，拿到坐标后调用 Open-Meteo 预报（已支持坐标查询）。
   - 失败或海外地点时回退到 Open-Meteo 地理编码。
4. 回答中写明省、市、区县，例如“河南省郑州市荥阳市”。
5. 测试：用真实返回格式做夹具，覆盖县级市、同名地点、海外城市、Key 缺失和超时。

完成标准：历史中“没有找到该地点”的天气问题，用新路径重放后命中率至少 95%；海外城市不受影响。

### 5.6 阶段 6：长期记忆

1. 保持 `docs/PERSONAL-MEMORY.md` 的原则：**只有用户确认的内容才保存**。
2. 回答完成后异步调用一次模型，提出 0–2 条候选记忆（偏好、事实、项目、专有词），附上原话出处。界面以“要记住吗？”的方式提示，用户确认后才写入。
3. 删除 `sessionProductState` 中“我喜欢吃 X”一类的正则抽取。历史中出现过把“吃”“的水果是”记成偏好的错误。
4. 记忆检索：给 `personal-memory.sqlite` 增加 FTS5 表（`tokenize='trigram'`），按问题内容检索最相关的 5 条。保留现有的字符数上限和账号隔离。
5. 迁移：首次启动时为已有记忆建立索引，失败时保留旧检索方式。

完成标准：评测集中的记忆问题全部取回正确条目；不会出现未经确认就保存的记忆。

### 5.7 阶段 7：延迟优化

1. 改写器与上下文准备并行进行；首问跳过改写器（见阶段 2）。
2. 火山 ASR 改为边录边传：录音时按 100–200 毫秒分包发送，停录后只等最后一包的结果。这需要改 `public/recording.mjs`、`src-ui/src/services/audioClient.ts` 和后端 ASR 会话。目标是把停录到出字从 P50 2.6 秒降到 1 秒以内（以真实测量为准）。
3. 搜索后预读网页（已实现）加缓存，同一会话内重复的搜索直接复用结果。
4. 每个阶段的耗时都写进执行记录，在历史详情中可以看到。

完成标准：问答 P50 和 P90 相对阶段 1 基线下降（目标值在阶段 1 后确定）；ASR 改造需要在真实麦克风上验收。

### 5.8 顺带修复

- 测试中约 20 个文件用 `server.listen(0)` 监听随机端口，偶尔落到 fetch 禁止的端口，报 `fetch failed: bad port`。统一改用 `test-support/http-listen.mjs` 的 `listenForFetch`，消除 CI 偶发失败。
- `question-context.mjs` 和 `daisy-question.mjs` 是压缩成长行的写法，难以审查。改写器上线后，按函数拆分并格式化，保持行为不变。

## 8. 需要用户决定的事项

1. **地理编码服务**：高德 Web 服务 API 或和风天气 GeoAPI。两者都需要注册并申请 Key，免费额度和商用条款需要用户自己核对。账号模式下 Key 应放在网关。
2. **改写器使用的模型**：默认用现有 `deepseek-v4-flash`。如果想再降低延迟或成本，可以评估更小的模型，但要先在评测集上对比。
3. **会话空闲多久开新对话**：建议 2 小时，也可以设成 30 分钟或 1 天。
4. **候选记忆是否开启**：会多一次模型调用，并且对话内容会发给模型生成候选（问答本身已经在发送）。建议默认开启，并在设置里允许关闭。
5. **改写器上线方式**：建议先用影子模式在你本机运行一到两周，再切换。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 改写器编造上下文中没有的地点或型号 | 程序校验：字段必须出现在原话中，否则丢弃；评测集里加入“不得出现”的检查 |
| 多一次模型调用，延迟和费用增加 | 首问跳过；限制输出 300 词元；超时 2.5 秒回退；阶段 3 减少的规划轮次可以抵消一部分 |
| DeepSeek 服务不可用 | 回退到规则；执行记录标明“已回退” |
| 放宽回答替换后，可能拿相近型号的资料作答 | 回答附核对提示；对象核对改用改写器结果后更准确；评测集覆盖相近型号 |
| 第三方地理编码 Key 泄露 | 只放本机配置或网关，状态接口不返回；遵守 `docs/GITHUB-UPLOAD-SAFETY.md` |
| 评测集包含个人信息 | 原始导出只放 `.local/`；提交的夹具人工改写并去标识 |
| 规则和改写器两套逻辑长期并存，维护成本高 | 改写器稳定后，把规则精简为校验和兜底，删除不再使用的分支 |
